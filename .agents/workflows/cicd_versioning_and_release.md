# Workflow: CI/CD Automated Versioning & GitHub Releases

This workflow specifies how DevTul handles automated semantic version bumping, continuous integration testing, and GitHub release publications when Pull Requests are merged into `master`.

---

## 1. Overview of the Automation Architecture

DevTul uses two synchronized GitHub Actions workflows:

1. **Continuous Integration (`.github/workflows/ci.yml`):**
   - Triggers on every Pull Request targeting `master` and every push to `master`.
   - Runs on both Linux (`ubuntu-latest`) and Windows (`windows-latest`).
   - Executes `flake8` linter and the full `pytest` test suite.
2. **Automated Release (`.github/workflows/release.yml`):**
   - Triggers automatically when a Pull Request is merged into `master`.
   - Also supports manual execution via `workflow_dispatch` with a choice of bump level (`patch`, `minor`, `major`).
   - Automatically bumps versions across `pyproject.toml`, `src/devtul/main.py`, and `src/devtul/__init__.py`.
   - Commits the version bump with `[skip ci]` and pushes the Git tag `v<version>`.
   - Builds Python distribution packages (`.whl` and `.tar.gz`) using `uv build`.
   - Compiles a standalone Windows executable (`devtul.exe`) using PyInstaller on `windows-latest`.
   - Publishes a formal GitHub Release with automated changelog notes and all attached assets.

---

## 2. Automated Version Calculation Rules

When a PR merges into `master`, the workflow inspects the PR metadata to determine the semantic version bump:

| Trigger Criteria | Bump Type | Example (`0.1.13`) |
| :--- | :--- | :--- |
| PR labeled `major` or `bump:major`, or PR title starts with `feat!:` or `breaking:` | **Major** | `1.0.0` |
| PR labeled `minor` or `bump:minor`, or PR title starts with `feat:` | **Minor** | `0.2.0` |
| PR labeled `patch` or `bump:patch`, or PR title starts with `fix:`, `chore:`, etc. (Default) | **Patch** | `0.1.14` |

## 3. Local Version Management Tooling

Agents and developers can preview or execute version bumps locally using the standardized script [`scripts/bump_version.py`](file:///c:/src/devtul/scripts/bump_version.py):

```bash
# View current active version:
python scripts/bump_version.py show

# Calculate and apply a patch bump (e.g. 0.1.13 -> 0.1.14):
python scripts/bump_version.py patch

# Calculate and apply a minor bump (e.g. 0.1.13 -> 0.2.0):
python scripts/bump_version.py minor

# Calculate and apply a major bump (e.g. 0.1.13 -> 1.0.0):
python scripts/bump_version.py major

# Explicitly set a specific version string:
python scripts/bump_version.py set 0.2.0
```

---

## 4. Manual Releases via `workflow_dispatch`

If a release needs to be published outside of an automatic PR merge:
1. Navigate to GitHub -> **Actions** -> **Release**.
2. Click **Run workflow**.
3. Select the branch (`master`) and pick the desired bump level (`patch`, `minor`, or `major`).
4. The workflow will bump the version, commit, tag, compile packages, build the Windows executable, and publish the release automatically.

## 5. Testing & Validation Artifacts Standards

Whenever developing, adjusting, or verifying CI/CD workflows, scripts, or build configurations:
- All programmatic test failures or validation outputs MUST be captured as `.artifacts/<session-slug>/impl_test_run_<n>.log`.
- All CLI verification and UAT dry-runs MUST be captured as `.artifacts/<session-slug>/uat_test_run_<n>.log`.
- **Mandatory Incrementing Policy:** Every subsequent run MUST increment the run number (`_1`, `_2`, `_3`, etc.). Never overwrite existing test logs.

---

## 6. Troubleshooting & Maintenance

- **Infinite Loops Prevented:** Version bump commits generated by the bot include `[skip ci]`, preventing the CI test workflow from triggering in an infinite loop.
- **Repository Permission Requirement:** The GitHub Action requires `Workflow permissions: Read and write permissions` enabled under repository Settings -> Actions -> General -> Workflow permissions.
